# Architecture

`niri-computer-use` is one binary. `serve` runs an MCP server over stdin and stdout, one process per agent session. `status` prints the readiness report and exits. `stop` and `resume` set and clear the stop flag, and `recover` clears the input-dirty marker. `engine` serves every client of one niri instance from one process, over a Unix socket (see [The shared engine](#the-shared-engine)).

## The shared engine

`niri-computer-use engine` serves every client of one niri instance from one process, which holds the one desk, crash guardian, event stream, accessibility connection and audit writer. It runs in the instance's runtime directory:

1. It takes an exclusive `flock` on `engine.lock`, waiting up to one second for an engine that is exiting. If another engine keeps it, this one exits 0 having changed nothing.
2. It empties `engine.log`, removes a stale `engine.sock`, binds a new one, sets it to mode `0600` and listens. Only then does it start the crash guardian, the event stream and the accessibility lookup, while connections queue.
3. Each connection must come from a process of the same user (`SO_PEERCRED`); others are closed. The client sends one hello line, at most 512 KiB, within two seconds: the hello version, the identity of the binary it runs (`/proc/self/exe`'s device, inode, size and modification time), the niri socket and Wayland socket it found, its `NIRI_COMPUTER_USE_UNRESTRICTED` and `NIRI_COMPUTER_USE_KEYBOARD`, its `HOME`, and its policy file as read (missing, unreadable with the error, or the text). The engine answers `{"engine": {"pid": <pid>}}`, or `{"refused": {"error", "detail"}}` with `engine_version` (another build or hello version), `session_mismatch` (another niri socket or display), `engine_busy` (64 connections already) or `bad_hello`, and closes.
4. After the hello the connection carries MCP, and the session's settings come only from its hello. A session ends when its connection ends or fails, or when it sends a line over 16 MiB.
5. Once it has had no connection, no lease held and no input cleanup pending for two seconds, it closes and removes `engine.sock`, still holding the lock, and exits. When its stop watcher ends, because the runtime directory was removed or replaced, it ends every session and exits at once. Either way it removes `engine.sock` only while the path still names the socket it bound: in a replaced directory, it may be a new engine's.

`status` reports under `engine` the serving process's PID, its mode (`standalone` or `shared`), how many sessions it serves and, for a standalone server whose client asked for shared mode, why it fell back. The engine's stderr is `engine.log`. Its session ids count up from 1 for its lifetime; a session's ended flag lives with the session, so the engine keeps nothing for a session after its connection is gone.

### The bridge

`serve` runs in shared mode when the policy file says `shared = true` or `NIRI_COMPUTER_USE_SHARED` is `1`. It decides once, before it reads anything from its client:

1. It connects to `engine.sock` (500 ms) and sends its hello. If nothing listens there, it creates the runtime directory if it is missing, which it is after someone removed it, takes `engine.start.lock`, so that bridges starting together start one engine, checks the socket again, and starts `/proc/self/exe engine` in its own process group with stderr appended to `engine.log`, then waits up to two seconds for the socket. It tries at most three starts, retrying every 20 ms to 200 ms, within five seconds.
2. If the engine refuses the hello, the socket's path is too long for a Unix socket (108 bytes), or nothing answers within the five seconds, it serves its client standalone, as without shared mode, and writes why to stderr.
3. Otherwise it relays lines both ways, unchanged. It keeps the ids and methods of the client's requests in flight and the client's `initialize`.

The hello carries no `PATH`: the engine runs `grim`, `wtype` and the other programs from its own `PATH`, the first bridge's, so a later bridge's `PATH` would change nothing and isn't compared.

Once relaying, the bridge never serves standalone. When the engine closes the connection, a read from it fails, or a write to it waits five seconds for the engine to read, every request in flight gets `engine_lost`: a `tools/call` as a tool result with `isError`, anything else as a JSON-RPC error. Only calls are limited, to 16 at once, so a client that sends `tools/list` without waiting can have more in flight than the queue to its stdout holds; each of these answers waits for room in that queue, so the writer runs between them. With nothing in flight, the session's next request gets it instead. After that, the next request starts a new connection as in step 1; if that fails, the request gets `engine_unavailable` and the one after tries again. Notifications that arrive with no engine are dropped, and so is a `notifications/cancelled` for a request already answered. On a new connection the bridge replays the client's `initialize`, which can only happen with nothing in flight, takes the first response with the client's own id for it, without passing it on, and sends `notifications/initialized`; then it sends the request.

A client line over 16 MiB ends the bridge: it stops relaying, writes one line to stderr and exits, closing stdout, and the engine ends that session. When the client closes stdin, the bridge closes its side of the connection and passes on what the engine still sends, for up to six seconds.

Nothing the client does or fails to do keeps the bridge from seeing that it closed stdin (`bridge/client.rs`). One task writes everything bound for stdout, the engine's lines and the bridge's own answers, in the order they come, from a queue of 32 lines; the relay queues the engine's lines without waiting. They come one at a time, as the engine writes them, so a full queue means the client has stopped reading, and ends the bridge at once. The `engine_lost` answers, which the relay makes in one burst, wait for room instead, until the client's stdout fails or its input overflows; a client that has closed stdin may still be reading. Each line has 30 seconds to be written and flushed, however slowly the client reads meanwhile; a write error or that deadline ends the bridge too. Lines the client has sent wait for the relay in a backlog of up to 32 MiB, twice the client line limit, so the reader reads on to the end of stdin while the relay waits. The reader never waits for room: a line that doesn't fit means the client has sent more than the engine has taken, and ends the bridge at once as well, without relaying that line or any waiting behind it. Ending this way, the bridge closes its connection, so the engine ends the session as on any disconnect, then writes one line to stderr, waiting at most 100 ms for it, and exits with status 1 without returning from `main`: tokio's stdout writes from a blocking thread nothing can stop, and the runtime would wait for it. The queue holds at most 32 lines of up to 256 MiB, the engine's line limit, so 8 GiB at worst, plus the line being written. Every wait of the relay, writing to the engine, reaching a new engine and replaying `initialize`, ends as soon as the client's stdin has ended or its stdout failed, unless the wait was over at once, so a line sent right before closing stdin is still relayed; the relay then closes the connection. A slow enough client thus loses its bridge, and with it outcomes it never received; as with `engine_lost`, nothing is replayed.

## Finding the session

Some clients start MCP servers with a short allow-list of environment variables; Codex passes on `HOME`, `PATH`, `USER`, `LANG`, `TERM` and a few more, but not `XDG_RUNTIME_DIR`, `NIRI_SOCKET` or `WAYLAND_DISPLAY`. At startup the server fills in each of the three that is unset or empty, and a variable that is set always wins:

- `XDG_RUNTIME_DIR`: the directory holding `NIRI_SOCKET`, with every symlink resolved, when that is set, because niri puts its socket in its own runtime directory; otherwise `/run/user/<euid>`, as logind creates it. Either only if it is a directory (not a symlink) owned by the effective user with mode `0700`. When the socket's directory fails that, the runtime directory is missing, not `/run/user/<euid>`: the lease and stop flag live there, and a server using another directory than niri's session would neither see its stop flag nor share its lease.
- `NIRI_SOCKET`: niri names its socket `niri.<display>.<pid>.sock` in its runtime directory. The server lists the runtime directory and keeps the sockets of that form, not symlinks, owned by the effective user, whose `<pid>` is a running process with `/proc/<pid>/comm` = `niri` and that accept a connection, within 500 ms, whose peer PID is `<pid>`; a socket a crashed niri left accepts none, even after its PID is reused, and stays where it is. When `WAYLAND_DISPLAY` is set, only sockets naming that display count; an absolute display path is compared with `<runtime dir>/<display>`. With exactly one, it uses that. With none, niri is `niri_unavailable` with a detail naming the directory it looked in. With several, such as two niri sessions of the same user, it picks none: `niri_unavailable` names them and says to set `NIRI_SOCKET`. `stop` and `resume` connect to nothing (`discover::Probe::Offline`), so they work while niri hangs: a socket counts when its `<pid>` is a running `niri`, without the connection, and they don't look for the display. That selection is weaker, since a socket a crashed niri left counts once its PID belongs to another niri, so it only ever picks where the stop flag goes, never where input goes; it still refuses to choose between several.
- `WAYLAND_DISPLAY`: the `<display>` in the niri socket's name, whether that socket was given or found, if `$XDG_RUNTIME_DIR/<display>` is a socket.

The session bus's fallback, `$XDG_RUNTIME_DIR/bus`, uses the runtime directory found this way too. Every child the runner starts, such as `grim`, `wtype`, `wl-paste`, the crash guardian and the paste keeper, gets the three as resolved on top of the environment it inherits, and never an inherited `WAYLAND_SOCKET`, which libwayland would use before `WAYLAND_DISPLAY`, so it reaches the same display and niri. The one exception is the shared engine a bridge starts: it gets the environment the bridge inherited, without the variables the bridge discovered, so it discovers the session itself the same way. `status` reports under `discovery` whether each of the three came from the environment or was discovered, or why it is missing. When both `XDG_RUNTIME_DIR` and `NIRI_SOCKET` are set and the socket, with every symlink resolved, isn't in that directory, resolved the same way, the server uses them as given and `discovery.warning` says so; another spelling of niri's runtime directory, through a symlink or `..`, is no warning. The server's own Wayland connections, for native input, the pointer, the paste keeper and `recover`, check on every connect that the display's peer PID is niri's. `wtype`, `grim` and `wl-paste` find the display by name alone, so right before each of them starts, and before the paste keeper starts, the server makes the same check on a connection of its own. When niri is gone the check gives `niri_unavailable`, and when another process serves the display, `session_mismatch`; either way input, screenshots and clipboard reads are refused before anything reaches the display. `status` makes the check on every call and shows the current result under `display_error`.

## niri requests

Each request opens a new connection to `NIRI_SOCKET`, writes one JSON line and reads one reply line, the way `niri msg` does. niri's replies carry no request id, so a reused connection could read a late reply as the answer to the next request. A fresh connection is dropped at its two-second deadline, so that can't happen.

A failed connect, or a connection that closes before replying, is `niri_unavailable`. niri's own error message, or a reply that doesn't parse, is `upstream_error`, with the message kept in `detail`. A request that passes the deadline is `deadline_exceeded`.

## Event stream

`serve` keeps one connection to niri open for its event stream. A task reads each event line, parses it as niri-ipc's `Event`, and applies it to niri-ipc's `EventStreamState`, the same reducer niri uses for its own replies. Tools read that state through a Tokio `watch` channel, so a snapshot comes from one moment and never waits on the reader.

On connect, niri sends its current state as a burst of events: workspaces, windows, keyboard layouts (if any), overview, config and screencasts. The state counts as initialized once the workspaces, windows and overview events have arrived. `desktop_state` waits up to two seconds for that, for example right after the server starts.

- If the connection ends, the state is dropped and the task reconnects after one second. Meanwhile `desktop_state` returns the last connection's error under the same names a request uses: `niri_unavailable` for a failed connect or a closed connection, `upstream_error` for a refusal or an unreadable reply from niri, and `deadline_exceeded` when niri doesn't answer within two seconds. `status` reports the stream as `disconnected`.
- If an event doesn't parse, the state is dropped and the task reconnects at once. A second unparsable event stops the stream until the server restarts: `status` reports `schema_incompatible`, and `desktop_state` returns `upstream_error` naming the event type. Ordinary disconnects don't count toward this.
- The `status` subcommand keeps no stream open, so it reports `event_stream` as null.
- The task stops, closing its connection, once the server drops its last handle on the stream.

## Cancellation and the audit log

rmcp marks a request as cancelled when the client cancels it, but it keeps running the tool. Each tool therefore runs its work through one helper that races it against the request's cancellation and drops the work when cancellation wins. Dropping a niri request closes its connection; dropping a `desktop_state` call only stops that call's wait, and the shared event stream keeps running. The helper also lets a session run at most 16 tool calls at once: one more gets a JSON-RPC error at once, isn't logged, and runs nothing.

The same helper writes one JSON line per call to `$XDG_STATE_HOME/niri-computer-use/audit.jsonl`, or `~/.local/state/niri-computer-use/audit.jsonl`, creating the directory, and any missing parent such as `~/.local/state`, with mode `0700` and the file with mode `0600`. Each line has the start time, the session (the MCP client's name and the server's PID), the niri instance, the tool, its argument metadata, the outcome and the duration. The `error` field is read only from the result's error name, never from its content: a stable name, `invalid_arguments`, `cancelled`, `internal` when the tool couldn't build its result, or null on success. Screenshot arguments are logged because they hold only targets, sizes, formats and the save path; no line ever holds an image, the clipboard's text or a window title. The passthroughs log metadata built in `audit.rs`: `niri_action` the parsed action's name and field names as niri-ipc spells them, numbers, booleans and nulls, with every string as `{"bytes": n}` and every list of strings as `{"count": n, "bytes": [...]}`, or, for JSON that isn't an action, `{"category": "invalid_action", "keys": n, "bytes": n}` and never its keys; `noctalia` only its argument count and byte lengths. The metadata is built before the call runs, so refusals and cancellations log the same. For an action tool that succeeded, the line also has `accepted` (true, false or null) and `observed` (an outcome name such as `focused` or `pending`), read from exactly those two fields of its result, which hold only a boolean and a name; they are null for read-only tools and for failures. A failed write doesn't fail the call; `status` reports the last one. Calls whose arguments rmcp rejects before the tool runs are not logged.

## Subprocesses

Every program the server runs goes through the runner. `runner::watcher` starts the crash guardian and `runner::companion` the paste keeper: each is not killed with its handle and learns of the server's end through its stdin. `runner::gated` starts a child with stdin held open until the caller feeds it, with one deadline from start to reaping, for `wtype`. `runner::run` gives no stdin, stdout and stderr collected, a deadline, and a process group of its own. Stderr is read to the end, keeping the first 16 KiB, so a verbose child never finds it closed. The call ends only when both pipes close, so a descendant that keeps one open holds it until the deadline. If the call times out or is cancelled before the child has been reaped, the runner kills the whole group, so anything the child started dies with it. Until the child is reaped its process ID can't be reused, so the kill can't reach another group. A child that exits normally is left alone, together with anything it left running. Stdout over the caller's limit is an error, and an error keeps the exit status and the kept stderr. After a kill, Tokio reaps the child in the background, so a zombie can briefly remain.

## Screenshots

`screenshot` reads niri's outputs, picks the target (a named output, the focused output, or the one output a region lies inside), and runs `grim -t jpeg -q 80` or `grim -t png` with an explicit `-s` scale and `-o <output>` or `-g "x,y wxh"`. Without `max_width` the limit is 1280 image pixels. The scale is the output's own, lowered when the capture's logical width times that scale is wider than `max_width`.

grim 1.5.0 sizes its image as `int width = logical width × scale`, which truncates (`render.c:145–146`). The server expects the same, and it nudges a lowered scale up by the smallest step until the truncated width is exactly `max_width`, because `max_width / width` can land just below it in floating point. A capture whose PNG or JPEG header disagrees with the expected size is an `upstream_error`. The metadata returns the output, its transform and layout origin, the captured rectangle in layout coordinates, the scale, the image size, and the capture time.

While this server holds the lease, each screenshot, the evidence screenshots included, is also kept in memory as a ref, and the result names it in `screenshot_ref`, such as `shot-5e1a90c2-4`; without the lease it is null. The middle part is random for each server process, so a ref another process issued, such as a server that ran before a restart, is unknown rather than someone else's capture. A ref records the output as niri described it, the captured rectangle, the scale, the image size, when the capture started and the event stream's connection. It separately retains the pointer space derived from the physical mode: niri 26.04's `compute_absolute_location` uses Smithay's `Space::output_geometry` (ff5fa7df), which ceils transformed mode size divided by fractional scale, whereas niri IPC truncates its logical size. A 1280-pixel output at scale 1.5 therefore maps pointer motion across 854 logical pixels, not IPC's 853. Both geometries must still match before input; an unknown physical mode refuses mapping rather than guessing. While its session holds the lease, the `screenshot` tool holds the action mutex throughout capture, excluding the next action and lease changes as well as waiting for a running action; without the lease it issues no ref and doesn't take the mutex. This does not freeze human input, other processes or animations. Evidence screenshots are already taken inside the action and do not reacquire the mutex. MCP cancellation releases the observation guard. The refs live beside the lease in the desk: taking or giving up the lease, including through the stop flag, drops them all, and ids count up for the server's lifetime, so a ref from an earlier lease is unknown rather than reused. A lease keeps its last 64 refs.

With `save_path`, `policy::Loaded::save_target` first checks that the policy file has a `capture_dir` (`save_not_enabled` otherwise, with nothing captured) and that the path follows the rules (`policy::SavePath`: relative, plain names, a `.png` file; a mistake is an argument error). Then, inside the same observation guard as the returned image, `observe::save` captures the target as a PNG with no `max_width`, so at the output's own scale, and `save.rs` writes it: the capture directory is created with mode `0700` if missing and opened, each subdirectory is opened with `O_DIRECTORY | O_NOFOLLOW`, and the file is created with `O_CREAT | O_EXCL | O_NOFOLLOW` and mode `0600`. A symlinked subdirectory, a missing one and an existing name, symlinks included, are argument errors; a failed write removes the file. The image to return is captured after, as asked, and its metadata gains `saved` with the path and pixel size. The two captures are a few milliseconds apart, so they can differ if the screen moved.

Downscaling happens in grim and costs time: on a 2560x1440 output, JPEG took about 14 ms at full size and about 100 ms at the default 1280 pixels.

## Noctalia and the lock state

Noctalia counts as installed when `noctalia` is an executable on `PATH` at startup. Only then does the server list `shell_status`, `shell_open` and `shell_close`, and `status` reports the same answer for the whole session, so the two never disagree. It counts as running when its socket, `$XDG_RUNTIME_DIR/noctalia-$WAYLAND_DISPLAY.sock`, answers `status` with a JSON object within two seconds. The server writes the whole fixed payload `/\x1estatus`, shuts down its write half and reads to the end, as Noctalia's own client does. Only the `noctalia` tool sends text from a tool's arguments (see below). Anything other than a JSON object is `noctalia_unavailable`, except an `error:` reply, which keeps Noctalia's text as `upstream_error`. `status` checks again on every call, so a Noctalia restart shows up.

The shell tools send `panel-open <id>` or `panel-close <id>` the same way. Every command is a `noctalia::Command` built from fixed words, and the only panel ids are those of `policy::Panel`: `control-center`, `wallpaper` and `tray-drawer`. Any other name, whatever Noctalia has, is `panel_not_allowed` before anything is sent; that keeps out the session menu, the launcher, which runs what is typed into it, polkit's prompt, the clipboard history, the setup wizard and the test panel. Noctalia carries a panel command out before it replies `ok`. A failed connect or an `error:` reply means nothing happened; a reply lost after the connect, or anything else, is `uncertain` with `accepted: null`. Noctalia sends no events, so the tool then reads `status` every 100 ms for up to two seconds until `activePanelId` shows the change.

The `noctalia` tool exists only when Noctalia is installed and `unrestricted` is on at startup. It joins its arguments with spaces after the `/\x1e` prefix, as `noctalia msg` does, over the same socket and deadline. A reply starting `error:` is `upstream_error` with Noctalia's text; any other reply is returned, cut at 64 KiB with `truncated`; a reply lost after the connect is `uncertain`.

The lock state comes from logind's `LockedHint` and from Noctalia's `locked`, and locked wins. niri sets the hint on the session in its own `XDG_SESSION_ID`, and only when it runs as the session instance (`niri --session`), so the server asks logind about that session, not its own: it finds niri's PID from the peer credentials of a connection to `NIRI_SOCKET`, checks that `/proc/<pid>/cmdline` has `--session`, reads `XDG_SESSION_ID` from `/proc/<pid>/environ`, and runs `loginctl show-session <id> -p LockedHint --value`. A server started from SSH, a TTY or a client that passes a minimal environment therefore reads the same hint as one started in the session. If niri's session can't be found, niri has none, or niri runs without `--session`, logind doesn't answer and Noctalia decides; without either answer the state is `unknown`. `status` reports the session asked, the source and logind's error, if any. A session ID that isn't plain letters and digits is refused before `loginctl` runs, so it can't be read as an option, and so are `self` and `auto`, which would name the server's own session. A plain `niri`, such as a nested one started by hand from a terminal, inherits the host's `XDG_SESSION_ID` but never sets the hint, so logind would say `no` on a locked screen; the `--session` check makes that `unknown` instead, and Noctalia decides. The nested harness also unsets the variable.

## Accessibility

At startup the server asks the session bus (`DBUS_SESSION_BUS_ADDRESS`, or else `$XDG_RUNTIME_DIR/bus`, where systemd puts the user bus and where libdbus, sd-bus and zbus look by default) for the accessibility bus's address with `org.a11y.Bus.GetAddress`, with one second to connect and one for the call. Only when that works are `elements`, `activate_element` and `set_element_text` listed, and `status.accessibility` says which it was and why, for the whole session, as with Noctalia. The server connects to the accessibility bus on the first `elements` call and keeps the connection, connecting again after one fails.

`elements` takes a window id. It reads the window from niri right then, refuses with `app_denied` when its `app_id` is on the deny list, and needs niri's PID for it. AT-SPI's registry lists the applications by bus name, and the bus, not the applications, says which process owns each name, so only the application whose process is the window's is ever called. Every call has a one-second deadline, the whole request three seconds; a call past its own second is `deadline_exceeded`. When the three seconds run out during the walk under the frame, the listing has what was read, possibly nothing, with `capped_reason: budget_exhausted`; before the walk, finding the application and its frame, it is `deadline_exceeded`. An object that disappears in the middle is skipped, and any other failure ends the call with the D-Bus error.

Of the application's top-level frames, the window is the one whose WINDOW-relative size is niri's `window_size`, within a pixel. Several such frames are told apart by the window's title, still several is `ambiguous_window`, and none at all is `not_accessible`. When none fits, the only frame, or the one named as the window's title, is still read, but nothing in it is placed: client-side decorations with shadows make GTK's frame larger than niri's window, and its coordinates then start elsewhere. The tree under the frame is walked depth first, into showing elements only, for at most 2000 objects (`capped` and `capped_reason: node_cap` say when that cut it short). The filters go into the walk, which stops once it found one more matching element than `limit`.

An element's box is `output origin + tile_pos_in_workspace_view + window_offset_in_tile + its WINDOW extents`, from niri's layout and outputs read for the call. It has none, with `unmappable`, when the frame didn't fit (`frame_size_mismatch`), the element isn't showing and visible or the window has no place in its workspace's view (`not_showing`), or it has no area (`empty`). While this server holds the lease, each listed element is kept as an element ref, named in `element_ref` (`elem-<tag>-N`, with the process tag of screenshot refs, numbered for the server's lifetime); the lease's last 1000 are kept, and taking or giving up the lease drops them, as with screenshot refs. A ref keeps the application's bus name, the object's and its frame's paths, the role, the window id and its PID, and a lineage that is never logged or returned: each object's path, index among its parent's children and a hash of its name, from the frame's child down to the element, the element last. The hash is std's `DefaultHasher` (SipHash), kept in memory only.

Before anything acts on an element ref, `elements::identify` checks that the object at the ref's path is still the element listed, since a toolkit may reuse an object for another record, as a virtualized list does with its rows. The ref's PID must still have an application on the bus with the ref's bus name; the window's accessible frame, found again among the application's frames as `elements` finds it, must be the ref's; walking down from that frame, each parent's `GetChildAtIndex` at the kept index must answer the kept path, so every link is vouched for by the parent rather than the child; and each object's name, read with one `Name` property call after its link, must hash as kept. Anything else is `element_stale`. A sibling inserted above the element shifts its index and makes the ref stale too: that fails closed, and listing again fixes it. The frame's own name isn't compared: a window's title changes on its own, and the frame is found by niri's window instead. A reused row keeps its place and path but shows another record, and its accessible name is that record's, so the names between the frame and the element catch it. `identify` compares the element's own name only for `activate_element` and `set_element_text` (`Names::All`), never for a pointer aim (`Names::Parents`): buttons relabel themselves when used, as counters do. An element action reads the element's name again after acting and keeps that hash in the ref, never an ancestor's, so its own relabelling doesn't make the ref stale; a name that changes later on its own does, which fails closed. A pointer click doesn't read the element afterwards, and M9's hundred clicks per ref relabel a counter each time, so a pointer aim leaves the element's own name to the role check and the agent. The listing has showing elements with a name or an action, or every showing element of a `role` asked for, filtered by `name_contains`, up to `limit`. Names are the app's text: returned, never logged; the audit log keeps the window id, the role, the length of `name_contains` and the limit.

## Runtime directory and the stop flag

Each niri instance has a runtime directory, `<dir>/niri-computer-use/<instance>/`, named after niri's socket with every symlink resolved (`control::runtime::Instance`): `<dir>` is the directory that holds it and `<instance>` its file name without `.sock`, for example `/run/user/1000/niri-computer-use/niri.wayland-1.1487`. `XDG_RUNTIME_DIR` plays no part, so servers for the same niri share the directory whichever runtime directory their clients passed and however `NIRI_SOCKET` spells the path, through a symlinked directory or a symlink to the socket with any name; a server for another niri, such as the nested harness, has its own. A hard link to the socket is another name for the same niri, not another spelling: resolved, it would name a directory of its own, so a socket with more than one link is refused by every name, the original included. The socket must resolve to a socket of the effective user's with one link, in a directory of the user's with mode `0700`; otherwise the process has no runtime directory, and so no lease, stop flag or marker, rather than one picked some other way: `acquire_desktop` fails with `niri_unavailable` and the reason, `status` shows it as `lease.error`, and `stop`, `resume` and `recover` exit 1 with it. Discovery, `stop`'s and `resume`'s included, accepts a socket only through this resolution. The check is made once, at the process's start: a server that resolved the socket before a link was made keeps its directory, and one started after the link is removed gets it again.

A process resolves the socket once, at its start, and connects to niri only at the resolved path from then on; the children it starts get that path as `NIRI_SOCKET`. A symlink retargeted later moves neither its niri nor its runtime directory. A restarted niri has a new PID, so a new socket name and a new runtime directory: servers started for the old instance keep its lease, guardian and marker there, and nothing they do reaches the new instance. Once the old socket is gone, nothing resolves to the old directory any more, so `recover` can't reach an old instance's marker; after checking that no key or button is stuck, a human deletes `input-dirty` there by hand.

`niri-computer-use stop` creates the directory with mode `0700` and the empty file `stop` in it with mode `0600`; `status` reports `stop: true` while that file exists. `niri-computer-use resume` removes it, and refuses while `input-dirty` exists in the same directory. Both need niri's socket: from `NIRI_SOCKET`, which niri sets for the commands it spawns, or [found](#finding-the-session) without it and without connecting to niri.

## The lease

One server at a time holds the lease on a niri instance. It is an exclusive, non-blocking `flock` on `<runtime dir>/lease`, a file created once with mode `0600` that the server never removes, so every server locks the same file. The kernel releases the lock when the holder's file is closed, which includes the process dying. The holder writes its PID, label (the MCP client's name and its own PID) and the time to `lease.json` for other servers' `status`; it empties the file before unlocking, and a record whose PID no longer exists names nobody.

`acquire_desktop` takes the lease only if the stop flag and the input-dirty marker are both absent. A runtime directory that can't be read counts as neither absent: the call fails rather than guess. A server watches its runtime directory with inotify from startup; whenever anything in it changes, it checks the stop flag again, and when the flag is set it gives the lease up. A directory that can't be read counts as stopped. If the watch can't be set up, `acquire_desktop` refuses, because a stop couldn't take the lease back.

Removing the runtime directory or the `lease` file while a server holds the lease would let another server lock a new file, and would leave the holder watching a directory nobody can reach. So the watcher checks, on every event and once a second, that the directory's path still names the inode it watches; when it doesn't, the watcher reports the flag as set and ends, the holder gives the lease up, and `acquire_desktop` refuses from then on with a detail that says to restart the server. Separately, the holder checks about once a second that `lease` still names the file it locked, and gives the lease up if not. The periodic checks exist because the kernel delays a directory's own deletion event while a file inside it is open, as the held lease is. The lease's mutex is the action mutex: an action holds it while it runs. Giving the lease up for a stop and the `lease` check both wait for that mutex, so neither is prompt while something holds it. An action's work doesn't keep them waiting: it checks for itself, without the mutex it already holds, `lease` once right before the work starts, after the readiness report, and while the work runs the stop flag on every change and `lease` every 100 ms; either ends the work and frees the mutex (see Actions). Everything else under the mutex runs to its end first: a readiness report, an action's or `acquire_desktop`'s, an action's evidence screenshot, and a screenshot the lease holder takes (see Screenshots), which waits at most for its niri requests, two seconds each, and grim's five seconds, twice with `save_path`. A stop or a replaced `lease` during one of those is acted on when it ends, and the next action, which checks both again under the mutex, sends nothing. `status` reads a copy of the holder kept beside the lease, so it never waits for a running action. Inside a server, the lease belongs to the session that took it, and so do its refs and `users_window`: another session's `acquire_desktop` gets `lease_held` and its actions `lease_required`, both without waiting for the owner's running action, and its `release_desktop` releases nothing. A `serve` process has one session.

A session ends when its client closes the server's stdin, reading it fails, or the client sends a line over 16 MiB, newline included. `session::LineLimit` checks every line a read ends, not only the last, so where the reads split the input doesn't matter; the bridge checks its client's lines with it too. The desk then drops the session's running action in whatever phase it is, the readiness check, the work or its evidence screenshot, along with a capture of the session waiting on or holding the action mutex, and gives its lease up the way a stop does, without giving focus back. An ended session can't take the lease again. Without this, rmcp would let a running call go on for up to five seconds after the client has gone, with the lease held. A dropped call can leave input cleanup running: a `wtype` still typing, or the releases of a dropped gesture or native key press, until niri has handled them and the input-dirty marker comes off. Each runs in a task of its own, `control::cleanup::spawn`, that ends ten seconds after it started (`cleanup::LIMIT`); a dropped native call's cleanup that takes over from a release that failed keeps that release's deadline. `serve` waits for them, up to the same ten seconds, before it exits, so the client's end doesn't cut one short and leave the marker behind. The steps have deadlines of their own, and steps that all came close to theirs would take longer: a native `paste`'s cleanup asks niri for the active layout (two seconds) and makes up to four Wayland round trips of two seconds each, for the releases, up to two keymap uploads and a dropped call's second zero modifiers, then waits six and a half seconds for the keeper's report and half a second for the marker's lock. Each step takes milliseconds when niri and the keeper answer. A cleanup still running at its deadline is dropped and leaves its marker, so the next action's `recovery_required` sends the user to `recover`, and a call still waiting for it fails with `deadline_exceeded` saying so. A `wtype` paste takes at most three seconds for `wtype`, then the same six and a half and half a second; a gesture's release, at most four and a half. An idle shared engine stops accepting clients only once none is pending, then waits the same way.

## The policy file and the lease decision

`$XDG_CONFIG_HOME/niri-computer-use/policy.toml`, or `~/.config/niri-computer-use/policy.toml`, is read once at startup. It lists `deny_input_app_ids`, an optional `capture_dir` (an absolute path or one under `~/`, resolved with `HOME` when used) and `[[preset]]`s, each with a `name`, a fixed `argv` and an `app_id`; unknown keys are errors. A preset whose program runs any command it is given (a shell, an interpreter, `env`, `sudo`, `setsid`, `busybox`, `uwsm` and similar, matched by file name with any version suffix removed, or `flatpak` with `--command`) is refused, and so is a terminal with arguments, because terminals run their trailing arguments as a command. Two presets with one name, an empty name, `app_id` or `argv` are refused too. A preset's `env` table is refused unless `unrestricted` is on.

`unrestricted` is on when the file's `unrestricted = true` or the server's `NIRI_COMPUTER_USE_UNRESTRICTED=1` says so; `policy::Unrestricted` keeps both sources for `status`, and any other value of the variable is reported there and leaves it off. With it on, the command-runner and terminal rules are skipped, `env` is allowed (names non-empty, without `=` or NUL; the program then without `=`), `launch` spawns `env -- NAME=value … argv` for a preset with `env`, `niri_action` sends gated actions, and the `noctalia` tool is listed. A missing file is valid; a file that can't be read or breaks a rule makes the policy `invalid`, and so does a missing `XDG_CONFIG_HOME` and `HOME`, because then nobody can tell whether a file exists.

`acquire_desktop` asks `policy::refuse_control` after the stop flag and the input-dirty marker, using the same report `status` builds: niri's version error first, then `read_only` for an unsupported niri version, events this build can't parse, or an invalid policy, then `screen_locked` for a locked screen and for an unknown lock state, so input only ever goes to a screen known to be unlocked. It asks under the action mutex, with the `lease` file already locked, so another server's lease refuses with `lease_held` before anything slow is asked, and a refusal gives the lock back. It reads the focused window it keeps as `users_window` there too, so waiting for a running action can't make either stale, and since both take time, it checks the session's end, the stop flag and the marker again before the lease is granted. Every action asks the same question again before it runs (see Actions). `launch` uses the presets. The pointer tools, `key`, `type_text` and `paste` refuse with `app_denied` when the focused window's `app_id` is on the deny list, `elements` when the window it is asked about is, `activate_element` and `set_element_text` when the element's window is, and `close_window` and `niri_action`'s `CloseWindow` when the window they would close is, named or focused. Focus and layout actions aren't checked: they don't send the app anything.

## Actions

`focus_window`, `focus_workspace`, `launch` and `close_window` act through niri's IPC. Each runs through `Desk::act`, which holds the action mutex for the whole action, so one server's actions run one at a time, and checks in this order: the runtime directory and the stop watcher, the stop flag (`stopped`), the input-dirty marker (`recovery_required`), the lease (`lease_required`), then `policy::refuse_control` with a fresh readiness report (niri unreachable, `read_only`, `screen_locked`), then that `lease` still names the file this server locked. The stop flag and the marker come first because they tell the agent to stop and ask the user, which taking the lease again wouldn't change. The report is gathered only once the cheap checks pass. While the action runs, the desk races it against the stop watcher: a stop drops the action, with any connection or wait it holds, returns `stopped`, and releases the mutex, after which the watcher's task takes the lease back. If the watcher itself ended, because the runtime directory was removed, the action is dropped the same way but fails with `upstream_error` saying to restart the server. A `lease` file removed or replaced, found before the work starts or while it runs, gives the lease up at once and fails with `lease_required`; a running action is dropped first, as for a stop, so anything niri had already accepted may have taken effect. An element action's work tells the desk right before its one call that acts may go out (`Desk::sending`, through `Recheck`); a stop or a moved `lease` that drops it after that is no error but the outcome `uncertain`, with `accepted: null` and the reason in `detail`, built from `Worked::CutAfterSending` without any further call or evidence screenshot (see Element actions). The flag is cleared under the mutex as each action starts. Cancelling the MCP request drops the action too, and the lease stays held. `status` never waits on the mutex; the holder's `release_desktop` does, so it returns once a running action has ended. Another session's `release_desktop`, or its end, returns at once while the lease is held: it has nothing to give up. No deadline covers a whole action; each step has its own, so the wait is at worst the sum of the running action's steps: for a niri action, the readiness report, the five-second wait and a screenshot (grim has five seconds); for `key`, up to 16 wtype calls of three seconds each; for `type_text`, up to 11; for `paste`, eleven seconds for the keeper to be ready, half a second for it to admit the key, the key, and six and a half for its report; with the native keyboard, one two-second round trip per key, up to 1000 for `type_text`. A stop doesn't wait for the work: it drops it, as above, though a readiness report or evidence screenshot already under way finishes first (see The lease).

`niri_action` runs through `Desk::act` like the others. Its JSON becomes a `niri_ipc::Action`, or an argument mistake; then `policy::refuse_action` refuses a gated action with `unrestricted_required` unless `unrestricted` is on, after the lease, stop and lock checks, so the refusal is audited like any outcome. `policy::action_gate` and the window-target match in `act/compositor.rs` are exhaustive matches without a wildcard arm, so a niri-ipc upgrade that adds an action fails to compile until both place it.

`shell_open`, `shell_close` and `noctalia` run through `Desk::act` too, but talk to Noctalia instead of niri: see Noctalia and the lock state. They send no input, so they write no marker.

Each niri action follows the waiting pattern of plan §7:

1. Register a waiter on the event stream. The waiter subscribes to the stream task's numbered events before it copies the replica's windows and workspaces, then skips events the copy already holds, so no event falls between the two. The task also announces the end of each connection by its number, and a waiter ignores the end of a connection older than the one its copy came from. If the stream has no initialized state within two seconds, the action fails as `desktop_state` would, and nothing is sent.
2. Check the arguments against that state: an unknown window or workspace id is an argument mistake, and nothing is sent. A focus target that already has focus is reported as `focused` with `accepted: false`, and nothing is sent either: with `workspace-auto-back-and-forth` in the user's config, niri answers a focus on the focused workspace by switching to the previous one.
3. Send the niri action on a new connection. A failed connect, a request not written whole, or niri's own error reply is an error, because niri can't have carried it out. A reply that is lost or unreadable after the request was written whole gives the outcome `uncertain` with `accepted: null`, because niri may have carried it out. niri answers an action after carrying it out, but the events it causes may come later.
4. Apply every later event to the waiter's copy and check the expected effect after each, for five seconds. Applying each event, rather than reading the replica when it changes, means a check sees every intermediate state, such as focus passing through another window. A disconnect ends the wait as `uncertain`, and so does falling 256 events behind.

The result separates `accepted` (true once niri acknowledged the request, false when nothing was sent, null when the reply was lost) from `observed`. While waiting, focus moving to a window that was neither focused before nor the expected target ends the wait as `interrupted`: for `focus_window` the target is the window, for `focus_workspace` any window on the workspace, and for `launch` any window opened after the launch, since an app may take focus before it sets its `app_id`, or an older window with the preset's `app_id`. Focus leaving every window, as when a shell panel opens, isn't an interruption. Nothing is ever retried.

An outcome in doubt, `timeout`, `pending`, `none`, `interrupted` or `uncertain`, comes with a fresh screenshot of the focused output at the default 1280 pixels wide, taken the way `screenshot` takes one. It is taken after the stop race, so a stop can't throw away an outcome already observed, but still under the mutex, so no other action of this server runs in between: its metadata is the result's `screenshot` field and the image follows the text in the result's content. A failed capture leaves the outcome as it is and adds `screenshot_error`.

- `focus_window` and `focus_workspace` (by workspace id) observe `focused`, or `timeout`. A workspace counts as focused once keyboard focus is also on its active window, or on no window when it is empty: niri reports the workspace and the window focus that follows it as separate events, so either alone would end the wait early. While the overview, the screenshot UI or a layer-shell surface with exclusive keyboard focus is open, focus stays off every window, so a switch to a workspace with windows reports `timeout`.
- `close_window` asks the window to close, as its close button would, and observes `closed` when niri reports it gone, or `pending` when it is still open after five seconds, for example behind an unsaved-changes dialog. Nothing escalates.
- `niri_action` finds the window the action is about: its `id` (or `window_id`), or the focused window when that is null; an unknown id is an argument mistake. Actions about no one window observe `sent`. Otherwise it waits up to one second for that window's reported state (`window_size`, `tile_size`, floating, focus, urgency, workspace, scrolling position) to change, then 200 ms more for a resize that comes in steps, and observes `changed`, `unchanged` or `closed`, with the window's state as `window`. niri 26.04 has no fullscreen flag, so fullscreen shows as the output's size.
- `launch` looks up the preset by name (`unknown_preset` otherwise) and asks niri to spawn its fixed argv; niri runs it detached, so the app outlives the server. It counts the windows with the preset's `app_id` that weren't open before, including a window whose `app_id` arrives later. After the first appears it keeps counting for another half second, because an app may open several, then reports `one` or `ambiguous` with their ids in `windows`; with none in five seconds it reports `none`. Focus moving to a window that was already open and has the preset's `app_id` means a single-instance app answered with the window it had: `focused`, with that window in `windows`. With `reuse`, one existing matching window is focused instead (`focused`), several give `ambiguous` with `accepted: false` and nothing started, and none launches as usual.

## Pointer input

`pointer_move`, `click`, `drag` and `scroll` run through `Desk::act` like the other actions. The work, in `input/pointer.rs`, then checks the arguments, looks the ref up, refuses with `app_denied` when the focused window's `app_id` is on the policy's deny list (`policy::refuse_input`), requests niri's outputs and refuses with `untested_output_config` unless `policy::pointer_support` accepts them, checks the ref (`refs::Shot::check`), turns each point into a layout point, and maps every layout point through the ref (`refs::Shot::aim_at`). A ref is refused past 60 seconds, when the event stream's connection differs from the one at capture, when its output's logical geometry, scale or transform differs from niri's answer just now, and for a pixel outside the image or a layout point outside the captured rectangle. A drag's steps are spaced evenly in layout coordinates.

A point is a pixel of the screenshot or an element ref, `elem-<tag>-N`, from `elements` under the same lease. An element is checked again right then, once, with no retry (`elements::aim`): niri still has its window, with the same process, and the deny list doesn't name the window's app; `elements::identify` finds the same element (see Elements); one round of calls to the element and its frame answers within the three-second budget; its role is the one listed (`element_stale` otherwise); it is showing and visible, has an area, and its frame still fits niri's window (`element_unmappable` otherwise). Its box is computed again from niri's layout and outputs read for that call, and its centre must lie inside the screenshot (`element_unmappable` with `outside_screenshot`). An object or application that is gone is `element_stale`, as is an id this lease didn't list.

The mapping is in `coords.rs`, with a type for each space: `ImagePx` (a pixel, which targets its centre) → `LayoutPt` (divide by the capture scale, add the captured rectangle's origin) → `OutputLocalPt` (subtract the output's origin) → the output's untransformed space (the inverse of niri's transform, written out per transform) → `ProtocolPt`, the `motion_absolute` arguments with extents of the untransformed logical size times 1000, clamped inside the output. Each encoded point is pushed back through a port of niri's forward formula (`compute_absolute_location` at v26.04) and refused if it would land more than 0.002 logical pixels away, which only a point off the output does.

`niri/pointer.rs` opens a Wayland connection of its own to `$XDG_RUNTIME_DIR/$WAYLAND_DISPLAY` (or the absolute `WAYLAND_DISPLAY`) for each gesture. It refuses unless the socket's peer is the PID that serves `NIRI_SOCKET`, so input can't go to another compositor. It binds the seat, `zwlr_virtual_pointer_manager_v1` version 2 and every `wl_output` version 4, and creates a virtual pointer bound to the screenshot's output by its name. Its socket is watched through Tokio's `AsyncFd`, so round trips never block the server's single thread, and each has a two-second deadline. Every step is one frame, flushed at once: a motion, a press, a release, or a wheel turn as `axis_discrete(15 × notches, notches)` → `axis_source(wheel)` → `frame`, the order niri needs (C12). Event times are milliseconds on the monotonic clock. After the last step a `wl_display.sync` round trip confirms niri has handled everything; only then is the result `sent`. A failure before any step reached the socket is an error like any other before input; a failure after one did is `uncertain` with `accepted: null`, because some input may have arrived.

The pointer counts a press as held as soon as it is sent and a release only once it reached the socket. Dropping it, which a stop or a cancelled request does to a running gesture, sends a release for every button still held, then destroys the device; niri releases nothing on its own (C8). `click` and `drag` wrap the pointer with the input-dirty marker, which names the pointer's output. After a whole gesture the marker comes off once niri has handled the release; if it can't be removed, the call fails with `upstream_error` saying the input was handled and the marker stays. A gesture dropped midway sends its releases at once and hands the pointer and the marker to a task of its own, which waits for niri to handle the releases before it removes the marker, or removes it at once if nothing was pressed yet; until then, every server refuses with `recovery_required`.

## Keyboard input

`key` and `type_text` run through `Desk::act`. The work, in `input/keyboard.rs`, refuses text over 1000 Unicode scalar values (`text_too_long`), reads every combination into wtype's arguments before anything is pressed, checks `expect` against the waiter's focused window (`focus_mismatch`) and the deny list (`app_denied`), then makes one `wtype` call per combination for `key`, and one per part of 100 scalar values, plus one for `Return` with `submit`, for `type_text`. Each call goes:

1. It writes the input-dirty marker, `pending`, naming the tool.
2. `runner::gated` starts `wtype -` (with `-M <modifier> -k <key> -m <modifier>` after it for `key`) with stdin as a pipe, in a process group of its own. wtype runs its arguments in order, so it waits at `-` before sending anything (C5).
3. The marker becomes `running`, with wtype's PID and its start time from `/proc/<pid>/stat`. If that fails, wtype is killed while it still waits, and the marker is removed, because nothing was typed.
4. A task of its own writes the text, or nothing for `key`, closes stdin and waits for wtype to exit, within three seconds of its start. wtype runs with `LC_ALL=C.UTF-8`, because it decodes stdin with the locale and outside a UTF-8 one stops at the first non-ASCII character while still exiting 0. A wtype that exited before reading, for example because it couldn't connect, closes the pipe; that write error is ignored and wtype's own exit status and stderr are reported. When wtype exits by itself the task removes the marker; a non-zero exit is an `upstream_error` with wtype's stderr. Past the deadline the runner kills wtype's group, and a wtype killed by a signal is treated the same way: the marker stays.

The task holds wtype, so a stop or a cancelled request, which drops the tool's work, doesn't end a wtype that is already typing: it finishes, and the marker comes off, within its deadline (plan §11). If the server exits, the runtime drops the task and wtype's group is killed, and the marker stays.

The waiter was registered before wtype started, so after each wtype exits, the work applies every event niri has sent since: if focus was on another window at any point, the result is `interrupted`, otherwise the next call goes out, and after the last one the result is `sent`, with `focus` saying whether `expect` was checked. So `submit`'s `Return` goes out only after all of the text did, and `submitted` says whether it was. If the event stream was lost meanwhile, it is `uncertain` with `accepted: true`: the keys were typed, but where focus went is unknown. A result that ends before the last part carries `typed`, the scalar values sent, or for `key` `pressed`, the combinations pressed, and a call that fails prefixes its error's detail with the same count, so the agent knows not to press Enter on half a message. The pointer tools report a stream lost after their input the same way.

## Element actions

`activate_element` and `set_element_text` run through `Desk::act`, so the stop flag, the input-dirty marker, the lease and the lock state are checked under the action mutex as for every action, and a stop drops the work before its one acting call if that hasn't gone out yet. Once the work has told the desk the call is going out, a stop or a moved lease still drops it at once, but the call's result is `uncertain` with `accepted: null` and the reason in `detail`, and nothing more is asked: no look afterwards and no screenshot, since the user stopped the agent or another server holds the desktop. The audit log records it as `uncertain` too. Neither writes the marker: no key or button can be left held. The work, in `elements/actions.rs`, sends nothing until every check passed, in this order:

1. The ref, looked up only once the gate passed (`element_stale` for one this lease didn't list). `activate_element`'s `action` must be one of the element's actions as `elements` listed them, which the ref keeps; without one, the element's first action that is `click`, `press`, `activate` or `toggle`, in any case, since Qt names its button's `Press`; otherwise an argument mistake that counts the element's actions and names their kinds (below), never the actions' own names. `expect: "none"` is an argument mistake: the focus check below can't be skipped.
2. niri, through the waiter's view: the ref's window still exists with the ref's process (`element_stale`), its `app_id` isn't on the deny list (`app_denied`), it has keyboard focus, and `expect` names it (`focus_mismatch` for either). A Noctalia panel or a lock screen holds keyboard focus with no window focused, so an element under it is refused here.
3. AT-SPI, one request with the usual one-second call deadline and three-second budget: `elements::identify`, as for the pointer (see Elements). `activate_element` reads the element's actions again and needs the chosen one still at the index it was listed at (`element_stale` otherwise); `set_element_text` needs the `EditableText` interface in `Accessible.GetInterfaces` (an argument mistake otherwise). Gone is `element_stale`. No frame guard: nothing is aimed, so a window with client-side decorations, whose frame doesn't fit, works. These are fast refusals; the last gate asks them again.
4. The last gate, `Gate::last`. Steps 2 and 3 are stale by the time they finish, and the app decides how long each of its answers takes, up to the call deadline. So the gate asks the app first and checks the server's own state after, so that no wait the app controls comes after a check of that state:
   1. The app, one call at a time, in the same request: `elements::identify` again; the tool's own read again, from which `activate_element` takes the index it sends (the chosen action must still be at the index it was listed at, so a changed action list can't make that index name another action: `element_stale`); the element's states (`GetState`); and last its role (`GetRole`), where `password_text` is `secret_field` (`policy::refuse_secret_field`) for both tools, since activating a password field can submit it, another changed role is `element_stale`, and not showing and visible is `element_unmappable` with `not_showing`. Role and states are read one after the other, not side by side, so a field that becomes a password field while its states are read is refused.
   2. The server's own state, none of which the app can hold up: the policy's answer from a fresh readiness report again (niri, the policy file, the lock screen: `screen_locked`), through the `Recheck` the engine passes in; the waiter then applies every niri event received so far, and a lost stream is `niri_unavailable`; step 2's checks run again on that view, and the focus it saw is the one reported; and last the desk's `checkpoint`: the stop flag, the input-dirty marker, that the session still holds the lease, and that the lease file is still the one locked, read without the action mutex the running action holds. `set_element_text` then needs the `editable` state the gate read (an argument mistake otherwise).
5. `activate_element` calls `Action.DoAction` with the index from the gate, `set_element_text` `EditableText.SetTextContents`, which replaces the whole text. Text over 64 KiB of UTF-8 was refused with `text_too_long` before anything else. Either call answering false is `upstream_error`: the app refused, as is an error it answered with.

What the gate doesn't see: the app changing the element after it answered, while the gate reads on and while it checks the server's own state, the longest part of which is the readiness report, bounded by its own niri and Noctalia deadlines, not by the app; and anything that changes between the end of those checks and the app taking the call, which is a check of in-memory state and one D-Bus message. niri, the desk and the app are asked apart, and nothing makes those reads and the call one step. A stop in that last moment still cancels the call if it hasn't been written yet.

The app's answer only means it took the request: it acts later, from its own main loop (research A4). `activate_element` then waits 300 ms on niri's event stream, ending at once if the window closes, and reads the element's role and states again. `observed` is `gone` when the window closed or the element is gone, `present` otherwise, with `element.states_set` and `element.states_cleared` naming the states that changed, or `unknown`, with the failure as `detail`, when the read failed otherwise; `unknown` is an outcome in doubt and gets a screenshot. The 300 ms covers GTK 3's and GTK 4's buttons, which answer an activation as they answer Enter, shown pressed for 250 ms and then clicked (`ACTIVATE_TIMEOUT` in `gtkbutton.c`); Qt acts at once. `set_element_text` reads `Text.CharacterCount` at once, since the app set the text before it answered: `matched` when it equals the text's count of Unicode scalar values, `differs` when it doesn't, with the count as `element.characters`, as when an app filters what it is given or a GTK entry keeps at most 65534 bytes, and `unknown` with `detail` when the read fails. Neither returns the element's name or text. The result's `element.role` is the role, `element.action` the action taken as `kind` and `index`: its index among the element's actions as `elements` listed them, and its kind, `click`, `press`, `activate` or `toggle` when its name is one of those in any case, `other` otherwise. An app names its actions, and may put anything in a name, so the server never repeats one back.

Nothing goes out when the request's budget is spent or its connection has closed: that is an ordinary error. Once the acting call may have gone out, no answer within its deadline, a connection lost before the answer, the bus's `org.freedesktop.DBus.Error.NoReply` (the app left without answering) and an answer that can't be read all mean the app may have acted. The result is then an outcome, not an error, like niri's lost replies: `accepted: null`, `observed: uncertain`, `detail` saying which call lost its reply and what the look afterwards saw, `element` as usual, and a screenshot, since it is an outcome in doubt. Nothing is retried. zbus sends and waits in one call, so an I/O error while writing the message counts as lost too, on the safe side.

A D-Bus error carries a message the app writes, and an app may put a field's text in it. Every AT-SPI call of an element action, the checks, the one acting call and the look afterwards, goes through a request built with `names_only`, so a failure's `detail` names the call and the D-Bus error's name, such as `org.freedesktop.DBus.Error.Failed`, and leaves the message out.

The audit log keeps the ref, the role the ref was listed with, the kind and index of the action that would be taken (or the kind of the one asked for, with a null index, when none can be chosen or the ref is unknown), `text_len` in Unicode scalar values for `set_element_text`, `expect` and `screenshot`, built by `elements::actions::logged` before the call runs, so refusals log the same. Never a name, a description or the text.

## Paste

`paste` runs through `Desk::act` like `key`. Its work, in `input/paste.rs`, refuses text over 1 MiB (`text_too_long`), checks `expect` and the deny list against the waiter's view, and only then starts `runner::companion("/proc/self/exe", ["paste-keeper"])`: our own binary, stdin and stdout piped, in a process group of its own, not killed when its handle drops. The server writes the text's length and the text; the keeper, in `input/keeper.rs`, connects through `niri/selection.rs` (niri's peer PID checked, as for the virtual devices), reads every MIME type of the current selection into memory, at most 16 MiB in all within two seconds, makes a round trip to niri and handles every selection it announced meanwhile, refusing if one came, and takes the selection with a source offering the text, `x-kde-passwordManagerHint: secret` and `application/x-niri-computer-use-paste`, a type of its own. It answers `{"report":"ready"}`, or `refused` with the reason, which the server returns as `clipboard_unsaved` before any key. Each of the keeper's steps until then has its own deadline: two seconds to find niri's PID, then two each to bind, save, make the round trip and take the selection (`keeper::TAKE`, ten seconds). The server waits that long plus a second for the keeper to start and read the text, so a slow niri ends the call with the keeper's own refusal rather than a server that gave up while the keeper still took the selection. A saved selection with the hint set to `secret` is refused too: the keeper would keep it past the password manager's own clearing. So is a copy made while saving: the restore would put the older selection back over it, and it could be a secret the check never saw. A saved selection with the keeper's own type is an earlier paste's text that a `kept` outcome left behind (see below): it isn't refused despite its hint, and afterwards the keeper clears the selection instead of restoring it, reporting `cleared` with a `detail` that says so. The decision is the pure step `keeper::previous`, unit-tested; that `take` feeds it the round trip's answer is checked only in the nested suite.

The server presses the combination with `keyboard::type_input_then`, so every gate and backend of `key` applies. Whatever commits the key, right before it can go out, takes the server's end of the keeper as an `Aftercare`: with wtype, the task that lets wtype past its gate, once it has its marker; natively, the device, right before the first stroke. It writes `k` and waits up to 500 ms for `{"report":"armed"}`, and only then sends the key; it writes `p` once the key is done, even if the key failed partway, and only then takes its input-dirty marker off. If nothing committed the key, the call writes `n`. The keeper answers `k` with `armed` only from its wait for the server's commands, while the text still holds the selection: it first makes a round trip to niri and handles every event sent before it, so a replacement already on its way counts, and a second `k` gets no answer. Without `armed` the key isn't sent: wtype is killed at its gate, or the native device sends no stroke. A keeper that answered with `done` instead has stopped waiting and restored, and its report goes to the call; otherwise the server writes `n` and waits six and a half seconds for the report, passing over an `armed` that came too late. The call fails with `upstream_error` saying the key wasn't sent and nothing was pasted, with what became of the clipboard, and the marker comes off as for any refusal before the key. The 500 ms covers a round trip to niri on a loaded system and stays well inside wtype's three seconds, which run while wtype waits at its gate. The keeper serves every read of the text in a task of its own, with a two-second deadline per transfer, and counts the reads that begin after `k`, since the target may read before `p` arrives. It waits for the first read until two seconds after `p`, then until 100 ms pass without a new one, and restores: a new source offering every saved type, or a cleared selection if nothing was selected. `n`, or end of stdin before `k`, restores at once, and so do ten seconds without `k`; the keeper then stops reading its stdin, so a later `k` gets no `armed`. If another client took the selection first, nothing is restored. Neither the end of stdin nor the quiet time proves the text still holds the selection, so before restoring the keeper makes a round trip to niri and handles every event sent before it: a replacement already on its way counts, and reads among them are served. A copy niri handles after that round trip and before the restore is still overwritten, as is one handled between the round trip after saving and the take; data-control has no request that sets the selection only if it is still the one seen. The keeper reports `{"report":"done","read":…,"clipboard":…}` and then serves the restored selection with no deadline until another client takes it or niri goes away, as `wl-copy` does; one keeper lingers at most, since the next paste takes the selection from it. Before it exits, whether it cleared, was replaced or stopped serving, it waits for every transfer it accepted to finish or reach its two-second deadline, so a slow reader still gets the whole text. The `Aftercare` waits six and a half seconds for the report (`keeper::FINISH`, the wait for the read and two round trips, plus half a second) and hands it to the call; without one the outcome's `paste.clipboard` is `unknown`.

A stop, a cancelled call or the session's end drops the call, but not a committed key: wtype's task and the native device's release run on in tasks of their own (see `control::cleanup`, which `serve` and an idle engine wait for), and they hold the `Aftercare`, so the keeper still gets `p` once the key is done and waits for the read before restoring. Their input-dirty marker stays until the keeper has reported, so no new input starts meanwhile, from this server or another; a marker whose input this process still holds is refused with `recovery_required` saying a cancelled call's input is still finishing, rather than sending the user to `recover`. A call dropped before the commit drops the keeper, which restores at once. After `k`, only `p` or `n` says the key can't still arrive. If the keeper's stdin ends after `k` without either, because the server died or a native release niri never acknowledged dropped the `Aftercare`, or ten seconds pass without either, the keeper doesn't restore: a late key would paste the saved clipboard, perhaps a password, into the app. It reports `kept`, and keeps serving the text until another client takes the selection, or the next `paste` replaces it and clears the clipboard. The user's earlier copy is then lost, which is the lesser harm.

Noctalia's clipboard service, in the nested session at least, ignores a selection that carries the password-manager hint and adopts the last selection it kept whenever the clipboard goes empty. So it keeps the pasted text out of its history; and if the keeper dies before restoring, Noctalia may offer the user's copy again.

## Screenshots after an action

Every action takes `screenshot`. `Desk::act` passes the outcome and a capture to `act::with_evidence` while it still holds the action mutex, so no other action can start before the image is taken. With `screenshot: true`, the image comes from `settle::screenshot`: a first look 50 ms after the action, then captures starting at least 100 ms apart until two in a row are the same bytes. The 1.5-second wall-clock budget includes the initial delay and capture work; it starts after acquiring the action mutex, not while queued behind another action. A capture still pending at the deadline is cancelled through the runner. Any successfully completed capture is kept, including a first frame observed at or after the deadline when the runtime resumes late; that frame is returned with `settled: false`, never as a missing-sample error. Only a timeout with no completed sample fails with `deadline_exceeded`. An app redraws at its own pace after niri handles the input, so an image taken right away can show the screen from before; two identical captures mean only that the sampled images matched, not that the application is semantically ready or that nothing changed between samples. A screen that keeps moving, such as a video, ends at the limit with `settled: false`. Without `screenshot`, an outcome in doubt still gets one capture at once.

## Waiting

`wait_for` changes nothing. Its window-condition wait does not take the action mutex. Both `screen_stable` and the optional final settled screenshot after a window condition hold the mutex only for each individual capture, releasing it between samples. Actions, release and stop's lease takeback can therefore run between captures rather than waiting for the whole visual-settlement timeout. A window condition registers a waiter on the event stream and checks the condition in `wait::met`, a pure function of the waiter's view, after every event, up to `timeout_ms`. `screen_stable` runs `settle` with `timeout_ms` as its budget, including time queued for individual captures. Stop and release may still wait for one capture already running to end; each capture has a runner deadline. Action-return screenshots remain inside the action mutex throughout their sequence.

## Giving focus back

`acquire_desktop` reads the focused window from the event stream and keeps it with the lease as `users_window`; a new lease forgets it. `release_desktop` with `restore_focus` runs `act::refocus` through `Desk::act`, so it passes the same checks as any action before it focuses that window, then gives the lease up whatever the outcome. A window that closed meanwhile is reported as `closed`, and nothing is sent.

## The input-dirty marker and `recover`

`<runtime dir>/input-dirty` says input may be stuck. It is one JSON object: the `operation`, the `phase` (`pending` before the input child starts, `running` once its PID is known), the writing server's PID, the time, the `child`'s PID and `/proc` start time, any pointer `buttons` pressed, native `keyboard` codes, and `released`, the time the crash guardian sent their releases. While the file exists, whatever it holds, `acquire_desktop` and every action refuse with `recovery_required`, `resume` refuses, and `status` reports it as `input_dirty`; a file that can't be read or parsed blocks the same way. The server writes it whole to `input-dirty.new` with mode `0600` and renames it into place, so a reader never sees half of it.

Every change to the file happens under `input-dirty.lock`, a lock file beside it that stays, taken without blocking and retried for up to half a second; the lock is held only for the file operations, never across input or a human's answer. A server writes a marker only if none is set, and each marker it writes carries an `owner`, unique to that input, which it compares under the lock before it updates or removes the file: a late change from an input whose marker `recover` already cleared never touches the next input's marker. The crash guardian and `recover` change only the marker they read: under the lock they check that the file still holds the same bytes before they note the releases or remove it. A lock that can't be taken in time fails the change, and the marker stays, with an error that says so. The refusal while a marker is set tells the two cases apart by `owner`: each process keeps the owners of the markers its input still holds (`marker::Written`), and drops one when that input clears its marker or gives up on it, as a cleanup does when `wtype` was killed by a signal or a release or removal failed. A marker this process still holds is "still finishing", and the agent can try again within seconds. One whose `server_pid` is another running process's, without the guardian's `released` note, may be too, but only that process knows, so the refusal says another server's input may still be finishing and to try again in a few seconds before `release_desktop` and `recover`. Whether it runs comes from `/proc/<pid>/stat`; the marker records no start time, so a PID reused since that server died still reads as running, which costs one retry; a field the owner set while finishing would need the marker rewritten as the input ends, for a wording that a single retry already covers. Any other, this process's own included, tells the agent to call `release_desktop` and the user to run `recover`, which takes the lease. A marker from a build before `owner` existed is read and recovered as before, but no server's own clear or update ever matches it. Servers from such a build don't take the lock, so running them beside this one leaves their marker changes unarbitrated.

`key` and `type_text` write it before `wtype` starts and remove it when `wtype` has exited by itself (see Keyboard input). `click` and `drag` write it, `pending` with the button, before they send anything, and remove it once their release has been handled; a gesture dropped midway removes it only after niri has handled its release (see Pointer input). Otherwise `niri-computer-use recover` is the only way to clear it, and only a human runs it:

1. It takes the lease, so no server can act meanwhile. If a server holds the lease, it refuses and names that server.
2. With a `child` in the marker, it checks that the PID still has the recorded start time, so a reused PID is never touched, then kills the child's process group, or the child alone if it doesn't lead one, and waits up to five seconds for it to exit. Without one, it lists the user's running `wtype` processes and ends them only if the human types `yes`, and only those that are still the processes it listed.
3. If the marker names pointer buttons and no child, it doesn't look for `wtype` processes: the pointer runs inside the server, which is gone or no longer holds the lease. It sends the release of each button from a fresh virtual pointer bound to the output the marker names, or niri's first enabled output if that one is gone, the way C8 cleared a button a killed pointer left pressed. If that can't be sent, it asks the human to press and release each button instead.
4. It prints the manual check (press and release Shift, Ctrl, Alt and Super, click once, check the application) and clears the marker only after the human types `yes`, and only if it is still the marker it read: one another input wrote meanwhile stays, and `recover` says to run it again. Anything else, including end of input or a child that didn't exit, leaves the marker in place.

### The crash guardian

A SIGKILLed server runs no `Drop`, and niri releases nothing when a virtual device goes (C8), so a button or key it held stays down. `serve` therefore starts `niri-computer-use guard <its PID>` through `runner::watcher` before anything else: `/proc/self/exe`, so a binary replaced since still runs, in a process group of its own, with stdout closed and stdin a pipe whose only write end the server holds. The guardian blocks on that pipe; when the server exits, however it exits, it reads end of file. Then:

1. Without a runtime directory, or without a marker that this server wrote naming native `keyboard` codes or pointer `buttons` and not yet `released`, it exits having sent nothing. A normal exit with no marker leaves no process behind. A `wtype` child outlives the server and finishes by itself, and an unreadable marker is the human's to inspect, so both stay for `recover` alone.
2. Within one ten-second deadline it takes the lease, waiting up to two seconds for a server refused by the marker or a running `recover`, reads the marker again under it, sends the keyboard releases and zero modifiers from a fresh virtual keyboard, in the layout niri has active or, when niri doesn't say, the marker's with a line on stderr saying so, and the button releases from a fresh pointer, exactly as `recover` does, each display connection checked against niri's peer PID, and writes the time into the marker's `released` if the marker is still the one it read. The fresh keyboard carries the compositor's map, so niri sends that map to clients again with the releases, replacing an extension the killed call left.
3. It leaves the marker in place. The keys are up, but whatever the input did to the application is unknown, so `acquire_desktop`, every action and `resume` still refuse until a human runs `recover`, which sends the same releases again and asks for `yes`. A failure is printed to the server's stderr, and the marker stays as it was.

In the nested suite the guardian's releases reached niri 1 ms after the kill for a held button, and 60 to 135 ms for native keys and modifiers while a redrawing window paced every round trip at the nested frame rate.

## Experimental native keyboard

`NIRI_COMPUTER_USE_KEYBOARD=native` selects `input/native.rs`; unset or `wtype` keeps the stdin-gated default. `niri/keyboard.rs` binds a version-7 seat (sealed, NUL-terminated keymaps), reads the keymap by offset rather than the inherited file cursor, and forwards the same map to `zwp_virtual_keyboard_v1`. The shared Wayland transport checks niri's peer PID and bounds every round trip to two seconds. libxkbcommon resolves direct symbols against the active layout. `input/keymap.rs` puts text symbols the layout lacks on named keycodes up to 255 that have no symbols, and checks with libxkbcommon that every other key's symbols and level modifiers, the layouts and the modifier names are unchanged, and that each added key changes no modifier or layout. The keyboard uploads that map for the call. niri sends a map to every `wl_keyboard`, the device's own included, whenever the map an input makes active differs in content from the active one: a virtual keyboard's key or modifiers make its own map active, a physical key the compositor's. The keyboard tells the maps niri sends apart by their libxkbcommon serialization, since niri re-serializes the map a device uploads, and it tracks the map installed on its device: the base it was bound with, the call's extension, or a base it uploaded since. A map that matches the installed one, or an extension the device installed before, however late it comes, is the device's echo; any other is a base map, the first one niri sent or a later compositor map after a layout or configuration change, which also ends the call as `uncertain`. So the old base the device's next key sends back after a configuration change isn't taken for the compositor's. A configuration put back to exactly the map the device holds can't be told from that echo: the device then puts the newer map back, and clients hold it until a physical key sends niri's own. At the end, whenever the device holds a map other than the latest base, an extension or the base it was bound with before the compositor's changed, it uploads the latest base map, with zero modifiers in the layout niri has active, asked with a `KeyboardLayouts` request right before, or, if niri doesn't answer that, the layout the event stream last reported; a layout the user switched to meanwhile stays. It waits for niri after the upload, and uploads a base map that arrived meanwhile in turn, twice at most. A call that needed no extension and saw no change uploads nothing. niri's active layout is the user's: it follows physical keys and `SwitchLayout`, never a virtual keyboard's group. A dropped call, cancelled or failed mid-stroke, can't wait for niri: it sends the releases and zero modifiers at once in the layout it last knew. Its cleanup task waits for niri to take them, asks niri, puts the latest base map back as above, then sends zero modifiers in that layout once more and waits before it checks that the base map came back. In the nested trials a dropped call's device saw its restored map come back only after that further input, and once the focused client got no modifiers event for one of two inputs, so both go out in the active layout. The nested input suite checks niri's config gaining a layout and a switch to it during a call, and calls cancelled after a switch, until one is dropped before it sees the switch; in each the focused client must be left in the layout niri has active. It also checks niri's config gaining a layout during an ASCII call, which needs no extension: clients must be left with the new keymap and the marker cleared. wev prints an event only when it next reads from niri, so for a cancelled call the check reads what wev printed before a later call's keymap. The call fails and keeps the marker unless the last map its own `wl_keyboard` received is the latest base map and the device holds that map too; a map that doesn't compile never counts, and a cancelled call's marker clears only on the same proof. Because the compositor's map is then niri's active one again, later physical or native keys send no map. Recover's fresh keyboard uploads the compositor's map, so its releases also send it back after a crash. Physical modifier preservation is not supported.

Native sends and acknowledges one complete key pair at a time, with focus/layout and stop checked before each pair. The focus/layout check reads only the events the stream has already delivered, without a timer: a zero-length timeout waits for tokio's next millisecond tick, which cost most of a 100-key call and let the keys fall into step with the nested niri's frame pacing. Stop/cancel explicitly release any tracked key and zero modifiers; marker removal waits for acknowledgement. The marker's optional `keyboard` field records conservative evdev `codes` and `group`, never text. Recover validates them, sends releases from a fresh keyboard, with zero modifiers in the layout niri has active, and still requires interactive confirmation. The marker's `group` is the layout at the call's start, so it is used only when niri doesn't answer, and recover then says the focused application may show another layout until the next key. After a SIGKILL the crash guardian sends the same releases at once, and the marker still waits for recover (see The crash guardian).

Native `keys` on click/drag/scroll holds modifier masks across the gesture. One marker includes both keyboard and pointer state. Normal completion acknowledges both; cancellation sends both releases immediately and acknowledges them in a cleanup task before clearing. Either way the held modifiers end as a dropped typing call's cleanup does, through the same `native::restore_active`: once niri has taken the release, the device asks niri for the active layout, puts the latest base map back with zero modifiers in it, and the marker clears only once its `wl_keyboard` and the device hold that map. The nested input suite checks a held drag whose niri config gains a layout, which niri then switches to, mid-gesture: clients must be left with the new keymap, wev in the second layout, and the marker cleared. A failure leaves the marker blocking input.

## Version rule

`niri-ipc` is pinned to `=26.4.0`. `status` compares niri's version reply, for example `26.04 (8ed0da4)`, with that pin: equal major and minor is `ok`, a different patch is `patch_warning`, and anything else, including a version that doesn't parse, is `read_only`.

## Errors

A failed tool returns `isError: true` with `{"error": <name>, "detail": <text>}` as structured content. The names are a stable contract for agents. A mistake in the arguments is different: rmcp answers arguments that don't fit the schema with `isError` and a plain-text message, and the server answers arguments that don't fit the desktop, such as an unknown output, the same way. An error inside the readiness report, such as niri being unreachable, is reported in the report rather than failing the `status` call.
